## The follow-ups

1. **Custom domain test.** The user's AdGuard serves `piforge.internal`. Set
   `domain: pooka.piforge.internal` in `/etc/pooka/pookad.yaml` on the host, add a
   wildcard record `*.pooka.piforge.internal` to 192.168.68.200 in AdGuard (the user
   does this), restart pookad. pookad issues a new leaf for the new domain from the
   same CA (ADR 0008; `pki.EnsureCert` renews when the names change). Expected: URLs
   print with the new domain, the existing `ca.pem` on clients still works, `pooka
   setup` reads the installed domain back (handoff 0007). Record the result in
   docs/benchmarks.md or a README note. No code expected unless something breaks.
2. **Live cert renewal.** `loadCert` runs once at start. Replace the static
   `Certificates` with `tls.Config.GetCertificate` that calls `pki.EnsureCert` at
   most once a day and serves the cached pair otherwise. Test with a fake clock
   through `EnsureCert`'s `now` argument. Small.
3. **URLs in `pooka ls`.** Add a URL column when any environment has one (daemon
   transport). `Env.URL` is already filled by the HTTP backend. Keep SPEC section 10's
   row for `ls` in step. Small.
4. **`sprite url` against the daemon.** The official CLI is not on the dev box.
   Install it under an isolated HOME (handoff 0005 has the command), point it at
   `https://api.192-168-68-200.sslip.io` with the CA in the system store, or at
   `http://192.168.68.200:7700`, and check `sprite url`, `sprite url auth public`
   and whatever it calls (`PUT /v1/sprites/{name}` with `url_settings`). Record the
   outcome in docs/sprites-api/README.md. Code only if the CLI sends a shape the
   daemon rejects.
5. **Activity-policy refactor.** The architecture review (handoff 0007) asked for
   one owner of activity policy and the idle decision instead of `Touch` calls in
   each handler. One approach: a middleware on the daemon mux that records activity
   for every request matching a method and path list, plus the exec session hooks,
   with `idle.go` the only reader. Keep SPEC 18.5's definition exactly (reads of
   information are not activity). Tests: `TestActivityFromRequests` in
   `internal/daemon/phase3_test.go` already pins the table; extend it. No behaviour
   change, so no ADR.
6. **Phase 3b tunnel ADR.** SPEC section 17 lists the candidate. Grill the user on:
   Cloudflare Tunnel versus frp versus nothing; whether `api.<domain>` is exposed
   through the tunnel; whether `public` means "through the tunnel" and `sprite`
   stays LAN or cookie only; a real certificate via DNS-01 on the user's own domain
   replacing the generated CA (`tls_cert`, `tls_key` already exist). Write ADR 0010.
   Design only, no code, unless the user says build.
7. **`pooka upgrade`.** Today a new release means re-running `install.sh` for the
   CLI and `pooka setup` for the host. One command should do both:
   - `pooka upgrade` with no flags upgrades the CLI and, when `host` is configured,
     the daemon. `--cli` and `--daemon` select one. `--version vX.Y.Z` pins a
     release; the default is the latest.
   - CLI side: the same steps as `install.sh` (ADR 0007): detect OS and arch,
     download the release archive, verify against `checksums.txt`, replace the
     running binary in place (write next to it, rename over it). Refuse when the
     binary is not writable and say which path.
   - Daemon side: reuse `installDaemon` and `fetchPookadScript` from
     `internal/cli/setup.go` over SSH, then `install-daemon.sh`, which keeps the
     config and restarts the unit. `--pookad <file>` pushes a local build, as setup
     does.
   - Print versions before and after: the CLI's `Version`, the daemon's from
     `GET /healthz` (`version` field). A `pooka version` command that shows both
     falls out of the same code and is worth adding.
   - Tests: the fake host for the daemon path (assert the fetch and install calls,
     as `setup_test.go` does); an `httptest` server with a fake archive and
     checksums for the CLI path, writing into a temp dir. Note the release-tag
     logic in `releaseTag()` and the dev-build fallback to the latest release.
   - SPEC section 10 row, README quick start, ADR only if the self-update
     mechanism needs a decision (for example signing); otherwise none.
